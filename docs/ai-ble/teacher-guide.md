# PICO 2 W AI SMART CLASSROOM 교사 지도안

실기 검증: NOT_RUN. 준비 조건 충족 전 수업 성공을 보장하지 않습니다.



기존 React/Vite 웹앱에 ?view=ai-ble을 추가한다. Next.js로 재구축하지 않는다. BLE는 Pico가 Peripheral/GATT server, Galaxy Chrome이 Central/GATT client인 구조로 한다. Colab에서 학습하고 Pico에서는 추론만 한다. 스마트폰 웹앱은 추론을 대신하지 않고 수신·시각화·라벨링·CSV 내보내기를 맡는다.

8차시 안에 가능하도록 교사가 수업 전에 펌웨어, aioble와 종속 라이브러리, USB 케이블, DHT11 제품 규격, Galaxy 브라우저 권한, 실제 센서 데이터 예비 자료를 준비한다. 학생이 BLE 내부 통신 코드를 처음부터 작성하는 것은 목표가 아니다. 학생은 센서 읽기, 데이터와 정답의 구분, 학습/평가, 학습된 조건 해석, 새로운 입력에 대한 추론을 설명하고 수정한다.

모든 모둠에 권장 구성: Pico 2 W with headers 1개, 데이터 USB 케이블 1개, 브레드보드, CDS, 고정저항 10kΩ, DHT11(3.3V 동작이 명시된 제품), 필요시 DATA 풀업 4.7~10kΩ, LED 1개와 330Ω, 검증된 부저 구동 회로, PC 1대, Android Galaxy 1대. 2~3인 역할 순환: 배선/코드, 관찰·라벨, 데이터 검증.

필수 교육 문장:
“AI가 판단하는 규칙은 사람이 정한 것이 아니라, 학습 데이터로부터 모델이 찾은 것이다.”
바로 이어서 설명한다: “다만 무엇을 정답이라고 부를지, 어떤 데이터를 모을지, 어떤 특성을 쓸지는 사람이 정한다. 모델의 판단은 그 선택과 데이터의 한계를 가진다.”

VENTILATE는 ‘이 수업에서 환기를 권고한 사례’라는 이름이다. CDS와 DHT11만으로 CO₂, 미세먼지, 산소, 감염 위험이나 실제 공기질을 측정할 수 없다. GOOD도 건강·안전 보장이 아니라 수업 라벨이다. 자동 환기 제어기라는 과장 대신 ‘교실 환경 행동 추천 분류 실습’으로 설명한다.

교실에서 50분 동안 온도·습도 네 상태를 충분히 만들 수 있다는 가정은 금지한다. 교사는 수업 전에 서로 다른 시간/조건에서 실제 센서로 데이터를 수집한다. 학생은 2·4·5차시에 직접 수집한 데이터를 포함해 학습하고, 7·8차시에 새 데이터를 따로 검증한다. 충분한 라벨이 없으면 부족 표시를 하고 실제 데이터 보충으로 해결한다. 임의 생성 데이터나 수치 임계값으로 자동 붙인 정답으로 네 상태 학습 성공을 꾸미지 않는다. 두 상태 예비 실습은 허용하되 네 상태 최종 프로젝트 완료와 구분한다.


## 8차시 상세안


공통 운영: 2~3인 모둠. 수업 시작 때 지난 CSV·모델 파일 보유 확인. 마지막 5분은 산출물 저장·출구표·정리. 각 시간표에는 고장 대응 시간을 포함했다. 교사가 라이브러리 설치·통신 내부 구현을 미리 준비하지 않으면 8차시로 완료하기 어렵다.

1차시 — Pico 2 W와 MicroPython
도입(0~5): Arduino에서 LED를 켜던 경험을 떠올리고 이번에는 스마트폰까지 연결하는 목표를 보여준다.
개념(5~15): RP2350, GPIO, 3.3V, ADC, MicroPython, Thonny의 역할. GPIO 번호와 물리 핀을 구별한다. W 모델의 LED는 Pin("LED")를 사용한다.
실습(15~35): Thonny 인터프리터/COM 확인 → Shell print → Pin("LED") 켜기/끄기 → 0.5초 주기 깜빡임 → Pico에 main.py 저장 → 재부팅 후 실행.
실패·회복(35~45): 충전 전용 케이블, PC에만 저장, GP25 복사, COM 점유를 진단한다. 5분 내 해결 안 되면 예비 보드로 교체하고 원인을 기록한다.
교사 발문: “코드의 16은 물리 핀 16일까요?” “Pico가 껐다 켜져도 실행하려면 어디에 저장해야 할까요?”
평가(45~50): Q1 GP16의 물리 핀은? 정답 21. Q2 5V Arduino 센서 신호를 그대로 연결해도 되는가? 정답 아니며 Pico GPIO 전압 규격을 맞춰야 함. Q3 내장 LED가 안 켜질 때 핀 설정은? 정답 Pin("LED").
성공 기준: 각 학생이 3.3V/GND/GP26을 지목하고 LED 재부팅 실행을 확인한다.
산출물: main.py, 준비 체크 4개. 심화는 깜빡임 주기 변경.

2차시 — 센서가 현실을 숫자로 바꾸는 과정
도입(0~5): “어두움이라는 말을 Pico는 어떻게 알까요?”
개념(5~15): CDS 저항 변화, 접점 전압, ADC 수치, DHT11 디지털 통신. 디지털 센서 출력이 단지 HIGH/LOW 한 값이라는 오개념을 교정한다.
실습(15~35): USB 분리 → CDS+10kΩ 회로 → GP26 값 확인 → 사전 준비 DHT11 배선 확인 → 3초 간격 측정. 손으로 CDS를 가렸다가 밝힌다. DHT11은 값이 즉시 크게 변하지 않아도 정상일 수 있음을 설명한다.
실패·회복(35~45): CDS 접점 없이 전원만 읽기, 브레드보드 전원레일 분리, DHT DATA/GND 혼동, 과도한 읽기. 물/뜨거운 물체/직접 입김으로 결로를 만들지 않는다.
교사 발문: “지금 30000이라는 값은 lux일까요?” “DHT11도 마지막에 숫자를 주는데 CDS와 무엇이 다를까요?”
평가(45~50): Q1 ADC가 직접 읽는 것은? 정답 전압. Q2 밝아질 때 값이 증가하는 이유? 정답 이번 배선에서 CDS 저항 감소로 접점 전압 증가. Q3 센서 오류를 0으로 저장해도 되는가? 정답 실제 0과 혼동하므로 안 됨.
성공 기준: 밝음/가림의 값 변화 3쌍, DHT 유효값 3회, raw/℃/%RH 단위를 구별한다.
산출물: 센서 코드와 관찰 기록. 이 단계 기록을 BLE 실측 CSV로 꾸미지 않는다.

3차시 — Bluetooth LE의 역할과 연결
도입(0~5): “선이 없는데 휴대폰은 어느 보드의 데이터를 받는지 어떻게 알까요?”
개념(5~15): Peripheral=자신을 알리는 Pico, Central=찾고 연결하는 폰, advertising=존재 알림, service=기능 묶음, characteristic=데이터 통로, notify=갱신 알림.
실습(15~35): 교사 제공 BLE 진단 코드 실행 → 키트명 확인 → Galaxy Chrome 링크 열기 → 연결 버튼 → 해당 키트 선택 → 테스트 카운터 수신 → 끊기/다시 연결.
실패·회복(35~45): 다른 스마트폰이 이미 연결, 인앱 브라우저, OS 권한/어댑터 문제. 앱에 카운터는 진단용이라는 배지를 붙이고 실측 수집을 비활성화한다.
교사 발문: “왜 페이지를 열자마자 연결창을 띄우지 않을까요?” “광고를 보는 것과 데이터 알림을 받는 것은 같은 단계일까요?”
평가(45~50): Q1 Pico와 Galaxy의 역할? 정답 Peripheral/Central. Q2 notify의 뜻? 정답 특성값 갱신을 연결 기기에 알림. Q3 같은 보드에 두 폰이 안 붙는 이유? 정답 본 수업은 단일 연결 설계.
성공 기준: 올바른 키트 카운터 수신, 1회 재연결, 역할 설명.
산출물: BLE 연결 체크. BLE 내부 코드를 전부 외우도록 평가하지 않는다.

4차시 — BLE 센서 대시보드
도입(0~5): 카운터 대신 실제 교실 값을 받는 차이를 질문한다.
개념(5~13): JSON key/value, 단위, 한 메시지와 여러 BLE 조각의 차이. 조각 헤더 암기는 요구하지 않는다.
실습(13~35): 통합 센서 송신 코드 실행 → light/temperature/humidity 카드 확인 → CDS 가림 반응 → 마지막 수신 시각·측정주기 확인 → 짧은 회차 수집 → CSV 1회 다운로드.
실패·회복(35~45): DHT를 분리했을 때 error/null을 관찰하고 다시 연결한다. 파싱 오류가 전체 화면을 멈추면 안 된다. 폰 배경 전환 후 stale 안내를 확인한다.
교사 발문: “화면 숫자가 남아 있으면 지금도 측정 중이라고 할 수 있을까요?” “JSON이 반만 왔을 때는 언제 화면을 바꿔야 할까요?”
평가(45~50): Q1 light의 단위? 정답 raw. Q2 마지막 수신이 오래되면? 정답 오래된 값 표시와 수집 중단. Q3 알림 10개가 측정 10회인가? 정답 조각일 수 있어 아님.
성공 기준: 실측 10회 이상, 세 카드 단위 표시, stale/센서 오류 상태 구별, CSV 파일 저장.
산출물: 첫 센서 CSV(라벨이 없으면 학습용에서 제외)와 연결 코드.

5차시 — AI 학습 데이터 만들기
도입(0~5): “같은 환경에 서로 다른 정답을 붙이면 모델은 무엇을 배울까요?”
개념(5~15): feature/label, 수집 회차, 편향, class balance, 잘못된 값, 정답 유출. state와 label을 분리한다.
실습(15~35): 센서 수치를 가린 상태에서 행동 라벨 합의 → 회차별 5개 측정 → 회차/라벨 분포 확인 → 사전 수집 실제 데이터와 비교 → 필요한 실제 자료 보충 → CSV 내보내기 → PC로 이동.
실패·회복(35~45): 한 라벨만 많음, 같은 순간 반복측정, 예측을 정답으로 복사, 회차 label 혼재, DHT 오류행. 부족한 클래스는 교사가 준비한 출처 있는 실제 자료를 사용하고 사용 사실을 기록한다.
교사 발문: “정답은 사람이 정하는데 왜 학습된 규칙이라고 할까요?” “연속 100행과 다른 날의 100행이 같을까요?”
평가(45~50): Q1 feature 세 개와 label 하나를 구분하라. 정답 light/temp/humidity와 행동 상태. Q2 seq를 feature로 넣으면? 정답 상황 대신 측정순서를 학습할 수 있음. Q3 환기 label이 CO₂ 측정을 뜻하는가? 정답 아님.
성공 기준: CSV 검사 통과, 네 상태 각각 독립 회차 4개 이상 확보 또는 구체적 부족 상태 기록. 부족하면 6차시 정식 학습 진입 전에 보충한다.
산출물: classroom_real.csv, 자료 출처·회차·클래스 분포 기록. synthetic로 부족을 메우지 않는다.

6차시 — Google Colab에서 실제 학습
도입(0~5): “처음 보는 문제에도 맞히는지 어떻게 확인할까요?”
개념(5~13): 학습/평가 분리, Decision Tree, accuracy, baseline, 과적합.
실습(13~35): CSV 업로드·검사 → 회차별 분리 → fit → predict → accuracy와 혼동행렬 → export_text에서 한 경로 읽기 → 자동 변환 셀 실행 → model.py 다운로드.
실패·회복(35~45): Colab 계정/네트워크, label 오타, 부족한 회차, 학습 정확도만 보고하기, 정수화 단위 혼동. 계정 문제는 교사 실행 화면으로 과정을 학습하되 해당 모둠 독립 실행을 추후 보충 표시한다.
교사 발문: “이 분기의 숫자는 누가 정했나요?” “90% 정확도인데 한 상태를 전혀 못 맞힐 수도 있나요?”
평가(45~50): Q1 test로 학습하면 안 되는 이유? 정답 새 자료 성능 평가가 무너짐. Q2 temperature_x10<=275 해석? 정답 27.5℃ 이하. Q3 모델과 다수 클래스 기준을 비교하는 이유? 정답 단순 찍기보다 나은지 확인.
성공 기준: 학습·평가 session 교집합 0, 실제 accuracy 출력, 한 오류 사례 해석, 모델 변환 검사 통과.
산출물: 실행한 ipynb, model.py, model-meta.json, model-tests.json. 정확도 일정 수치 달성을 완료 조건으로 삼지 않는다.

7차시 — Pico Edge AI
도입(0~5): “인터넷을 끊으면 판단도 멈출까요?”
개념(5~13): Colab의 학습과 Pico의 추론, 학습된 if와 사람이 임의 작성한 if의 차이.
실습(13~35): model.py를 Thonny로 Pico 루트에 저장 → MODEL_ID 확인 → 고정 테스트 입력으로 원본과 일치 확인 → 실제 센서로 predict → LED와 부저 상태 표시 확인.
실패·회복(35~45): PC에만 model.py 저장, import 캐시/재시작, feature 순서 바뀜, 센서 배선 반대, models 누락 시 GOOD fallback. 교사 예비 키트에서도 학습 출처를 확인한 모델만 사용한다.
교사 발문: “if문이 보이면 무조건 AI가 아닌가요?” “Pico는 지금 규칙을 새로 배우고 있나요?”
평가(45~50): Q1 학습 장소/추론 장소? 정답 Colab/Pico. Q2 임계값을 손으로 바꾸면 같은 학습 모델인가? 정답 아님. Q3 LED 출력 정책도 AI가 배웠나? 정답 사람이 정한 상태 표현.
성공 기준: 실기 model-tests 전부 일치, 실측 예측 출력, 모델 없는 경우 오류 표시, 임계값 출처 설명.
산출물: 모델 ID와 실기 테스트 결과. 소리는 교사 허용 모둠만 짧게 확인.

8차시 — AI SMART CLASSROOM 통합
도입(0~5): 센서→학습→Pico 추론→스마트폰 경로를 학생이 설명한다.
개념·계획(5~10): 최종 검증은 학습·기존 test와 분리한 새 관찰이다. 인터넷 없는 Pico 추론과 웹 페이지 로딩을 구분한다.
실습(10~30): 새 조건/시간에서 라벨을 먼저 기록 → 센서 10회 이상 추론 → Pico state/LED/폰 결과 비교 → 예상과 다른 사례 분석 → 연결 끊김·복구.
발표·상호검증(30~40): 2분 설명+1분 질문을 모둠끼리 병렬 진행. 모든 모둠을 교사가 순차 평가하는 시간으로 계산하지 않는다. 교사는 5~7차시 관찰 기록과 8차시 핵심 시연을 합쳐 채점한다.
실패·회복(40~45): 새 데이터 성능 저하, 영역 밖, 상태 흔들림, 재연결 실패를 한 가지 선택해 개선 계획 작성.
평가·정리(45~50): Q1 ‘이 모델은 어떤 라벨을 누구의 자료에서 배웠는가?’ Q2 ‘틀린 판단 하나와 가능한 원인은?’ Q3 ‘정확도를 올리려면 어떤 새 데이터를 모을까?’ 모범 방향: 출처·라벨 기준·부족 조건을 구체적으로 설명.
성공 기준: 센서→Pico predict→출력→BLE→폰의 한 흐름 실제 시연, 새 실측 10회 이상 결과/오류 기록, 미지원 환경 안내, CSV/모델/해석 제출.
산출물: 최종 실측 검증 CSV(학습 CSV와 구분), 간단 결과표, 한계와 개선 3문장.


## 루브릭


모둠 산출물 70점 + 개인 이해 30점. 모든 학생에게 동일한 개인 질문 2개와 후속 질문 1개를 준다. 정확도 자체에 높은 점수를 주지 않는다. 정당한 실패 분석이 단순히 높은 accuracy보다 중요하다.

A. 배선·센서 검증 / 15점 (모둠)
15: 핀·전압·단위 정확, CDS 변화와 DHT 오류 구분, 실측 증거.
11: 동작하나 설명/오류 처리 한 항목 부족.
7: 일부 센서만 검증, 교사 도움 후 원인 설명.
3: 동작·단위·배선 근거 대부분 미제시.

B. 데이터·라벨의 타당성 / 20점 (모둠)
20: 실제 출처, feature/label 분리, 네 class와 독립 회차, 오류/중복 검사.
15: 실제 자료와 라벨 일관성 확인, 분포/회차 한 항목 미흡.
10: 편중/부족이 있으나 이를 확인하고 실제 보충 계획 제시.
5: 라벨 출처나 데이터 검증이 불명확.

C. 학습·평가·모델 변환 / 20점 (모둠)
20: fit/test 분리, accuracy·baseline·혼동행렬 해석, tree 출처와 변환 동등성 확인.
15: 학습/평가·변환 완료, 해석 또는 검증 한 항목 부족.
10: 실행 결과는 있으나 누수/변환 검증 문제가 남음.
5: 모델 생성 과정·평가 근거가 대부분 없음.

D. 실기 통합·복구 / 15점 (모둠)
15: Pico 추론→LED/부저→BLE→폰, 새로운 데이터·재연결·오류 처리를 시연.
11: 기본 통합 성공, 새 자료/복구 중 한 항목 미흡.
7: 부분 통합 성공과 구체적 고장 진단.
3: 통합 근거가 거의 없음.

E. 원리 설명 / 20점 (개인)
20: 사람이 정한 label과 데이터가 만든 분기, 학습/추론, state/label 차이를 스스로 설명.
15: 세 영역 중 두 영역 정확, 질문 후 나머지 보완.
10: 한 영역 정확하거나 도움을 받아 설명.
5: 코드 복사 수준으로 설명 근거 부족.

F. 한계·개선 / 10점 (개인)
10: 실제 오분류 사례, 센서 한계, 다음 수집 조건을 연결해 제안.
7: 한계와 개선은 있으나 근거 연결 일부 부족.
4: 일반적인 개선 한 가지만 제시.
1: 한계·개선 근거 거의 없음.

미제출/증거 없음은 해당 영역 0점. 학교 평가계획의 기본점수 규정이 있으면 그 규정에 맞게 사전 공지 후 환산한다. 하드코딩한 분기나 synthetic를 학습 모델/실측이라고 제출한 경우 C의 모델 학습 증거는 인정하지 않고 수정 제출 기회를 준다. 기기·통신 장애 자체로 개인 이해 점수를 감점하지 않는다. 개인정보·건강정보 제출을 요구하지 않는다.
