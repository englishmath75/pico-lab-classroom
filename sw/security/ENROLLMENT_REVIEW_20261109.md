# SW 학생 등록 변경 검토

상태: 구현 후보. 운영 적용 안 함. Firebase 관리자 인증 미완료로 현재 운영 전체 규칙·학급·교사 권한의 최신 확인은 BLOCKED.

## 사용자 결정

- 최초 Google 로그인 후 학교·학년·반·실제 이름을 입력하고 담당 교사에게 승인 요청한다.
- 2026-11-09 추가 지시: 기존 승인은 테스트뿐이므로 승계하지 않는다.
- 기존 교사 권한은 유지하고 MK 및 상용 Python 서비스는 수정하지 않는다.

## 변경 동작

- 선택값에 기본 학년/반을 지정하지 않는다. Google 표시 이름에서 학적이나 실명을 추측하지 않는다.
- 서버 관리 문서 `config/swEnrollment`에서 학교, 학년도, 학년/반 선택 범위와 승인 담당 수업을 읽는다.
- `users/{uid}.enrollment`에 학교·학년도·실제 학년·반을 저장한다. `displayName`에는 학생이 입력한 이름을 저장한다.
- 기존 `classId`는 SW 담당 교사의 수업 명단 식별자이며 학생 실제 학적과 분리한다. 학생 화면에는 이를 학년·반으로 표시하지 않는다.
- 신규 등록과 소속 정보 없는 이전 테스트 계정은 항상 pending으로 등록한다. 이전 승인만으로 저장 권한이 열리지 않는다.
- 실제 신규 등록을 승인한 이후에는 학생이 승인 상태·소속을 직접 바꾸거나 이용 정지를 우회할 수 없다.
- 이전 테스트 명단은 교사 승인 화면에서 제외되며 학생이 재등록한 뒤 다시 나타난다. 학습물은 일괄 삭제하지 않는다.
- 입력값 확인, 계정 전환, 서버 저장 확인, 승인 상태 갱신, 모바일 단일 열을 처리한다.

## 운영 승인 전 확인할 구체적 변경

1. Firebase 콘솔에서 현재 전체 규칙을 다시 읽고 보관한다. `integration-proposed.rules`는 저장소 기준 참고본일 뿐 운영 전체 규칙으로 간주하지 않는다.
2. 현재 규칙에 아래 최소 SW 변경만 적용한 diff를 만든다. `enrollment-proposed.rules`는 에뮬레이터 후보이며 바로 게시하지 않는다.
   - `config/swEnrollment`: 인증 사용자 읽기만 허용, 클라이언트 쓰기 금지.
   - SW users 생성: 학교 계정 도메인·필수 학적·카탈로그 일치·pending 강제.
   - 학생 수정: 소속 없는 테스트 계정의 재등록, 또는 실제 승인 대기 신청 정보 수정만 허용.
   - SW 저장 승인 판정: 실제 학적 등록과 교사 승인 모두 필요.
   - 교사 상태 변경: 소속 등록된 담당 학생의 pending→approved, approved→blocked, blocked→approved만 허용.
3. `config/swEnrollment` 1개 문서를 생성한다. 제안 JSON의 학교는 마산무학여자고등학교, 2026학년도, 1~3학년, 1~12반 선택이다. 실제 운영 범위 및 담당 `class-2-1` 존재·활성·교사 권한을 확인한 뒤 최종 확정한다.
4. `staff`, MK cohorts, public_users, 2027 규칙, 학습물 경로 및 저장 한도는 바꾸지 않는다.
5. 위 규칙 변경과 설정 문서 생성에 대한 사용자 승인을 받은 뒤 SW만 기존 Pages 경로로 배포한다.

## 검증 구분

- 단위검사: 필수 입력, 고1 학적, 학교 도메인, 테스트 승인 무효화, MK/상용 규칙 원문 동일성.
- 에뮬레이터: 승인 대기 저장 차단, 담당 교사만 승인, 잘못된 학교/학년/반 거부, 정지 우회 차단, 기존 학습물 보존, 계정 전환.
- 브라우저: PC/390px 모바일, 실제 가입 폼, 교사 승인 UI, 별도 브라우저 컨텍스트 복원.
- 실제 학교 Google 로그인·운영 DB·학교 PC: 인증과 운영 적용 전에는 BLOCKED/NOT_RUN. 에뮬레이터 검증을 실제 계정 검증으로 보고하지 않는다.
